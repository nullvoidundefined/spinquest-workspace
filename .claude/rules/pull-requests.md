# Pull requests

Reviewer attention is the scarce resource. Write the PR for the reviewer, not for the record.

## Description

- PR1. Say what changed, why, and anything a reviewer must know before approving. The diff covers the rest.
- PR2. No history. Leave out decisions already settled with the reviewer, timestamp or ordering justifications, spec-vs-implementation tables and review-bot finding IDs. That story belongs in commits, if anywhere.
- PR3. A design or risk note earns its place only when the point is dangerous or non-obvious: locks, irreversible migrations, rollout order, a revert that needs care. Routine reasoning stays out.
- PR4. AI disclosure is one line in the template's field and appears nowhere else.
- PR5. The template's quality checklist is a self-check. Do not tick or annotate its items. Read it and be ready to justify the work against it.
- PR6. Do not reply to a reviewer's general guidance item by item. A short acknowledgement is enough.

## Code comments

- PR7. Comment only oddities or constraints the code cannot show. A header that walks through routine behavior is too much.
